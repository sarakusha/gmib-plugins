# gmib plugins

Официальные плагины и публичный каталог для
[gmib](https://github.com/sarakusha/gmib).

## Каталог

gmib загружает каталог по стабильному адресу:

```text
https://raw.githubusercontent.com/sarakusha/gmib-plugins/main/catalog.json
```

Индекс генерируется из `plugins/*/manifest.json`. Готовые архивы хранятся в GitHub Releases этого
репозитория. GitHub Pages публикует дополнительную копию каталога.

## Плагины

- [`informer`](plugins/informer/README.md) — часы, дата и погодные слайды; настройки как локальная PWA с уведомлением о применении и экраном «Запустите GMIB» без связи; кеш погоды с пулом до 10 ключей Яндекса (сайт и умный дом), суточными бюджетами, дополнительным обновлением со страницы Яндекса без ключа и тестовым режимом, погодные подложки, иконки показателей, выбор полей даты, одна/две строки даты и времени, настройки по группам, плавная защита от выгорания с уровнями дистанции и скорости и предпросмотр по размерам экранов GMIB (включая 704×192 и 320×192);
- [`icehockey`](plugins/icehockey/README.md) — самостоятельный хоккейный пульт и LED-табло; составы необязательны;
- [`sports-roster`](plugins/sports-roster/README.md) — общая база команд и составов, локальная PWA;
- `parking-counter` — минимальный полный пример со страницей вывода и управления;
- `shader-screensavers` — адаптивные WebGL-заставки;
- `yoshka-esh` — портретное парковочное табло с фирменным оформлением.

## Проверка и сборка

```sh
pnpm install
pnpm validate
pnpm build
pnpm build:catalog
```

Архивы появятся в `dist`, итоговый индекс — в `catalog.json` и `site/index.json`. Сборка
воспроизводима на разных ОС: служебные файлы исключаются, а timestamps и файловые атрибуты ZIP
фиксируются.

## Проверка разбора Яндекс Погоды

При изменении выдачи сайта можно отдельно проверить парсер Informer, без запуска GMIB.
Команда не использует API-ключи, не меняет настройки плагина и не расходует квоту API.

```sh
npm run informer:check-weather -- --url https://yandex.ru/pogoda/ru/yoshkar-ola --lat 56.6333 --lon 47.8908 --save-dir /tmp/informer-weather-check
```

Она загружает одну страницу, до четырёх разрешённых JS-файлов для поиска идентификатора
фонового запроса и один лёгкий ответ. JavaScript читается как текст. В новом каталоге
сохраняются `page.html`, `asset-*.js`, `light.txt` и `report.json`; существующий каталог
не перезаписывается. Для повторной загрузки укажите новый каталог. `--save-dir` необязателен.

Повторная проверка сохранённых ответов работает без сети:

```sh
npm run informer:check-weather -- --page /tmp/informer-weather-check/page.html --light /tmp/informer-weather-check/light.txt --lat 56.6333 --lon 47.8908
```

Можно передать только `--page` или `--light`, а также проверить сигнатуру в JS через
`--asset /path/to/asset.js`. Для URL доступны `--mode page`, `--mode light` и `--mode both`
(по умолчанию). Режим `light` с URL тоже загружает HTML и JS для обнаружения запроса.
Запуск без параметров или с `--help` показывает справку.

JSON-отчёт содержит температуру, состояние, иконку, ветер, давление, влажность и прогноз.
Поля, отсутствующие в лёгком ответе, могут быть `null`; при проверке обоих ответов прогноз
и дополнительные показатели сохраняются из HTML. При HTTP-ошибке, нераспознанном формате,
отсутствии прогноза в HTML или идентификатора фонового запроса возвращается код `1` с
указанием этапа. Успешная проверка возвращает `0`. Повторов и фонового опроса нет.

Если проверка перестала проходить, сохранённые ответы позволяют обновить
`plugins/informer/dist/weather-page.cjs` и повторять проверку без новых запросов к Яндексу.
Команда сама не изменяет парсер и не устанавливает обновления. После исправления запустите
`npm test` и пересоберите Informer.

## Публикация версии

Плагины публикуются выборочно: тег `<plugin-id>-v<version>` выпускает только
указанный плагин. Например, `informer-v1.0.1` создаёт релиз Informer 1.0.1.
Каталог общий и содержит ссылки на отдельные релизы плагинов.

До первой пубикации манифест остаётся на `1.0.0`: локальные итерации не считаются релизами.
Кеш service worker версионируется независимо, например `icehockey-ui-1`; номер меняется при изменении
кешируемой PWA-оболочки.

1. Обновите `version` в `plugins/<plugin-id>/manifest.json`.
2. Проверьте проект командой `pnpm validate`.
3. Создайте и отправьте тег `<plugin-id>-v<version>`.

Например:

```sh
git tag parking-counter-v1.0.1
git push origin parking-counter-v1.0.1
```

GitHub Actions проверит соответствие тега манифесту, соберёт `.gmib-plugin` и создаст GitHub Release.
Каталог публикуется через GitHub Pages при попадании изменений манифеста в `main`.

Подробная спецификация Plugin API и требования к содержимому находятся в [AGENTS.md](AGENTS.md),
полные переносимые типы — в [gmib-plugin-api.d.ts](gmib-plugin-api.d.ts).
Необязательная convention для plugin-owned HTTP schemas описана в
[docs/plugin-http-api.md](docs/plugin-http-api.md); она не вводит общий формат `/settings` и не
требует выпуска gmib при добавлении маршрута, если хватает существующего Plugin API.

## Plugin API 1.1

Поддерживаются `dependencies`, `contributes.sports` и `localOnly`. Хост предоставляет SQLite,
сервисы зависимостей, монотонные часы и cleanup; актуальные контракты находятся в
`gmib-plugin-api.d.ts`. Старые плагины с `^1.0.0` сохраняют совместимость.
SQLite-драйвер поставляет gmib: нативные зависимости в архив плагина добавлять не нужно.

## Документация и проверка

Инструкции по запуску, возможностям и ограничениям находятся в `README.md` каждого плагина;
общий README описывает только каталог, SDK, сборку и публикацию. Если README есть, сборщик
включает его в архив плагина. `pnpm test` запускает сценарии SQLite и спортивного состояния
на Node 24+; нативных runtime-зависимостей эти тесты в плагины не добавляют.

План дальнейшего развития спортивных плагинов: [регламенты, общие библиотеки и темы](docs/sports-evolution-plan.md).
Эталонная игровая логика документируется рядом с исходниками Matchpad в `docs/sports`.
Каталог [`docs/matchpad`](docs/matchpad) в этом репозитории хранит ссылки и отличия облегчённых
плагинов от эталона.

Повторно используемая спортивная логика находится в `packages/sports-core`, а форматирование
и общие функции представления — в `packages/sports-ui`. Плагины перечисляют runtime-копии в
`sports-libraries.json`; после изменения библиотеки выполните `pnpm sync:sports`. Сборка и
валидация проверяют совпадение копий, а готовый архив не зависит от репозитория.

## Plugin API 1.2: вывод и плееры

GMIB 5.7.1 добавляет разрешение `player.control` и методы
`output.listPlayers/setPlayerState`. Экран переключается эксклюзивно, без
активации главного окна GMIB. Контракты, ошибки, совместимость и примеры:
[docs/plugin-output-api.md](docs/plugin-output-api.md).

## KeUSB-24R

Проект: [plugins/keusb-24r](plugins/keusb-24r/README.md). Управление реле, расписания,
условия освещённости и PWA. Требуется GMIB 5.7.4 или новее с Plugin API 1.3. Сборка: `node scripts/build.mjs --plugin keusb-24r`.
